    Chapter 0

    The problem we started with

    There are 2,225 BBC News articles sitting in folders on a disk. Somebody asks a simple question: which of these articles talk about both oil and price? This chapter explains why the obvious answer is a bad one, and what we are going to build instead.

    The two things we carry through every chapter

    The queryoil AND price
    The articledata/raw/bbc/business/027.txt — "Steel firm 'to cut' 45,000 jobs"

    Watch these two change shape at every stage. By Chapter 10 you will know exactly what happens to each of them, and why this particular article is not in the answer.

    The problem right now

    Right now we have nothing but files. To answer oil AND price the only thing we can do is open every file and look inside it. In Python that is about four lines:

    It works. It is also the wrong shape, for three separate reasons.

    1. The cost is proportional to the collection, not to the answer. Computer scientists write this as O(N) — the work grows in step with N, the number of documents. Whether three articles match or three hundred, we still open all 2,225 files and read all 854,490 whitespace-separated words. Every single time. A second query pays the whole cost again.
    2. It cannot combine conditions cheaply. oil AND price is easy, but (oil OR gas) AND prices AND NOT football means re-scanning with a more complicated test. There is no way to compute part of the answer once and reuse it.
    3. Substring matching is wrong. "oil" in text is true for the word boiler, spoiled and turmoil. To fix that you need to split the text into words properly — and once you are doing that, you may as well do it once and keep the result.

    That last observation is the whole idea of this project. Do the reading once. Keep what you learned. Answer every future query from the notes instead of the files.

    The idea

    Instead of asking "what words does this document contain?", turn the question round and ask "which documents contain this word?". Store the answer. That store is called an inverted index, and building one is what the next ten chapters are about.

    Here is the pipeline the assignment asks for. Every following chapter builds exactly one of these boxes, in this order.

    The code

    There is no code yet — this chapter is the statement of the problem. But it is worth seeing the shape of the repository first, because the file names are the chapter names.

    Why it is built this way

    The obvious alternative is to use a ready-made search library. Whoosh, Lucene or a database with a full-text index would answer oil AND price in one line of setup.

    That was rejected because the assignment is about understanding the machinery, not using it. The brief says the Boolean operations "must use the postings lists created by your system", and asks for a study of Porter's stemming algorithm. A library would hide exactly the parts we are being asked to explain. So tokenisation, stemming, the dictionary, the index, the merges, the wildcards, the edit distance and the scoring are all written from scratch here. The only outside help is NLTK's English stop-word list and its WordNet lemmatiser, and NLTK's own Porter stemmer used purely as an independent check in the tests.

    What you now have

    A clear statement of the objective, taken from the assignment brief: transform raw documents into a searchable vocabulary and inverted index, process Boolean queries against the postings lists that system produced, and tolerate spelling and vocabulary variation.

    And a measured baseline for how much work the naive approach costs.

    854,490 whitespace-separated words that a brute-force scan re-reads on every single query, across 2,225 documents and 5,041,385 bytes (about 4.8 MB) of text.
    Check yourself — the naive scan gets "oil" in text wrong for three English words. Name one.

    boiler, spoiled, turmoil, oilseed — any word with the letters o-i-l inside it. Substring matching does not know where words begin and end. The fix is to split the text into words first, which is Chapter 2.

    Chapter 1

    Getting documents in, reliably

    Before you can index anything you need to agree what "document number 26" means, and be certain it means the same thing tomorrow. This chapter is about that promise.

    The problem right now

    The corpus is 2,225 .txt files spread across five folders. Everything we build from here on refers to documents by a number, not by a filename — a postings list is a list of integers like [2, 8, 11, 15, ...], because integers are small and fast to compare.

    Two things can go wrong, and both are quiet failures rather than crashes.

    1. The numbers move. If the file order changes between runs, document 26 is Steel firm 'to cut' 45,000 jobs today and something else tomorrow. Every saved index, every result file, every number in the report silently becomes wrong. Nothing raises an error.
    2. The text is corrupted on the way in. Our article contains (£16.7bn; 24.1bn euros). The £ is stored as two bytes, C2 A3. If Python is left to guess the encoding it will use whatever the operating system prefers — on Windows that is usually cp1252, which reads those two bytes as two separate characters and turns £ into Â£.

    The idea

    Load every file once, in a sorted order, and hand out numbers by counting. Sorting is what makes the numbering reproducible: sorted() in Python is deterministic, so the same folder always yields the same list, therefore the same numbers, on any machine.

    The code

    First, what a document is. A dataclass is Python shorthand for "a little record with named fields".

    Second, loading. This is the only function in the project that touches the disk.

    Why it is built this way

    Decision: load everything into memory at once. The alternative, streaming documents one at a time and never holding them all, is what a system with a hundred million documents must do. Streaming would force the numbering into a separate pre-pass and re-open every file for evaluation.

That was rejected because Chapter 2 compares five different processing configurations against each other, and they can only be compared fairly if they all start from identical raw input. Any processing done here would silently apply to all five and make the comparison meaningless.

    Chapter 2

    Text is messier than it looks

    A sentence is a string of characters. An index needs a list of words. Getting from one to the other involves more decisions than you would expect, and each decision has a cost as well as a benefit.

    The problem right now

    We have raw text and we need words. Take the headline of our running article:

    raw textSteel firm 'to cut' 45,000 jobs

    Splitting on spaces gives ["Steel", "firm", "'to", "cut'", "45,000", "jobs"]. That is wrong in three ways: 'to and cut' carry stray quote marks, 45,000 carries a comma, and Steel here will never match a user who types steel.

    Some vocabulary before we go further.

    • A token is one occurrence of a word. The sentence "the cat sat on the mat" has six tokens.
    • A type is one distinct string among those tokens. That same sentence has five types, because the appears twice.
    • A term is a type after we have finished processing it — what actually goes into the dictionary. If we lower-case, then the tokens Steel and steel are two tokens, two types, but one term.

    Our job in this chapter is to decide how tokens become terms.

    The idea

    Do it in layers, and make each layer switchable so you can measure whether it helped. Four layers, each optional:

    1. Tokenise — find the word-shaped runs of characters and throw away the rest.
    2. Case folding — lower-case everything, so Steel and steel become one term.
    3. Stop-word removal — drop extremely common words like the, of, to. A stop word appears in so many documents that its postings list is enormous and tells you almost nothing.
    4. Stemming or lemmatisation — collapse word families, so job and jobs become one term. That is Chapter 3.

    The code

    The tokeniser is a single regular expression. Everything about how words are cut is in this one line, which makes it easy to reason about and easy to change.

    Now the switchable configuration. Again a frozen dataclass, but this one is callable — defining __call__ means you can write STEMMED(text) as if the object were a function.

    And the five named configurations. They are cumulative — each adds one layer to the one before, except the last which swaps stemming for lemmatisation.

    The query so far

    typedoil AND price
    termsoil, price — both already lower-case, neither is a stop word
    noteThe query must be processed by exactly the same configuration as the index, or the words will not match. Chapter 6 shows the function that guarantees this.

    Why it is built this way

    Decision: keep intra-word apostrophes and hyphens. The alternative is to split on every non-letter, which would turn Netherlands-based into Netherlands plus based and don't into don plus t. Splitting invents a token t that means nothing, and it loses the fact that Netherlands-based is a single compound. Keeping them costs us a rare mismatch when a user types dont, which Chapter 8's spelling correction can handle.

    Decision: use NLTK's stop-word list rather than writing one. A hand-written list is a hidden variable — nobody can reproduce your results without your exact list. NLTK's English list is published, fixed and citable. The cost is that it is not tuned for news: it contains will, which in a business corpus also appears as a name.

    Decision: case fold, knowing it loses information. Lower-casing turns US (the country) into us (the pronoun). Once folded, there is no way to tell them apart, and a search for the United States will also return every article containing the word "us". The same happens to Apple the company and apple the fruit, and to Bush and bush. The alternative — so-called truecasing, which decides case per occurrence from context — is a research problem of its own. Folding was chosen because users type lower-case, and the measurements bear this out: macro F1 rises from 0.7032 to 0.9044 when case folding is switched on. The us problem is visible in the results too: us is the second most frequent term in the whole collection, with 3,478 occurrences.

    Decision: numbers are kept, and 45,000 becomes 45 and 000. This is a known weakness. The regex has no rule for digit grouping, so a comma inside a number splits it. The alternative — a special case for numeric patterns — was left out because none of the 30 evaluation queries search for numbers, so it would add complexity that no measurement would ever exercise. It is listed as a limitation in Chapter 10 rather than hidden.

    A way to turn any string into a list of terms, in five measurable variants, applied identically to documents and to queries. You can now say precisely what document 26 contributes to the index, and you can measure what each processing layer costs and buys.

    Check yourself — stop-word removal deleted 41.8% of all tokens but only 176 distinct terms. Why such different numbers?

    Because stop words are few but astonishingly frequent. NLTK's English list has a couple of hundred entries, so at most a couple of hundred terms can disappear from the dictionary. But those few words — the, of, to, and — account for roughly two of every five tokens in ordinary English prose. Removing 176 types therefore removes 357,654 tokens. This is exactly the trade you want: the index gets much smaller while the vocabulary, which is what determines whether a query can be answered at all, is almost untouched.

    Chapter 3

    Words come in families

    A user searching for investment almost certainly also wants articles about investing, invested and investors. This chapter builds the machinery that makes those one term, and is honest about what it breaks along the way.

    The problem right now

    After Chapter 2, document 26 contributes the term jobs, and also producers, years and investing from elsewhere in the article. A user who searches for job gets nothing from this article, because the string job is not equal to the string jobs.

    This is not a rare edge case. In the evaluation set, query q24 is the single word investment, and a document is judged relevant if it contains any of invest, invests, invested, investing, investment, investments. Without some way of collapsing that family, the system can only ever find the documents that happen to use the exact surface form the user typed. Measured: the nostop index, which has no family collapsing at all, reaches macro recall 0.8686; it simply cannot do better on those queries.

    The vocabulary is also bloated. 33,805 distinct terms, and a large slice of them are just other spellings of terms already present.

    The idea

    Stemming is chopping standard endings off words so that members of the same family reduce to the same string. That string is the stem. It does not have to be a real word — producers stems to produc, which is not English. That is fine, because the stem is only ever used as a lookup key. As long as every member of the family produces the same key, the family is found. Making several different words map to one term is called conflation.

    Porter's 1980 algorithm does this with about sixty hand-written rules applied in a fixed order over eight steps. The crucial extra ingredient is that most rules only fire if what is left over is "long enough". Porter measures length in a specific way.

    Write any word as a run of consonants and vowels. Group them:

    [C] (VC)m [V]

    The square brackets mean "optional". m, the measure, counts how many vowel-then-consonant groups sit in the middle. Roughly, m counts syllable-like units. Small m means a short word that cannot afford to lose any more letters.

    The code

    Four small helper functions come first. Every rule in the algorithm is expressed in terms of them, so getting them right is most of the work.

    Now the eight steps, each implementing one table of rules from the 1980 paper.

    Try it — watch a word pass through all eight steps

    This runs the same algorithm as the Python above, ported line for line. Type any word, or pick one of the examples. Highlighted rows are steps where the word actually changed.

    Three honest failures, all real.

    1. technology and technological do not meet. technology ends in y, so step 1c turns it into technologi and nothing else fires. technological has no y; step 3 turns ical into ic giving technologic, then step 4 removes ic giving technolog. Two members of one family, two different stems. In this corpus technologi has document frequency 241 and technolog has 16 — they are two separate entries in the dictionary that should have been one.
    2. player never reduces to play. Step 4 would strip er, but only if the surviving stem has measure greater than 1. play has measure exactly 1, so the rule refuses and player survives intact. Meanwhile play itself goes through step 1c and becomes plai. So the family splits into player and plai.
    3. one becomes on. Step 5a strips the final e when the measure allows it. on has measure 1 and is not consonant-vowel-consonant, so the rule fires. The number word now collides with the preposition. This happens in the first paragraph of our running article.

    These are not bugs in the implementation. The test suite checks this code against NLTK's own Porter stemmer and they agree; the behaviour is what the published 1980 algorithm specifies. They are the intrinsic cost of a rule-based stemmer that never looks a word up in a dictionary.

    Why it is built this way

    Decision: implement Porter from the paper rather than import a stemmer. The assignment asks you to "study the principles of Porter's stemming algorithm". Calling nltk.PorterStemmer() would produce identical output and demonstrate nothing. The library version is still used, but only in tests/test_porter.py, as an independent oracle: if our stem and NLTK's stem disagree on a word, our implementation is wrong. That is a much better use of the library than using it to do the work.

    Decision: eight separate functions, not one big one. A single function with sixty if branches would be shorter. Splitting by step means each function corresponds to one numbered table in the paper, so a reader can check the code against the source. It also makes trace() possible, which is what powers the widget above — you cannot show a step-by-step trace of a monolith.

    Decision: stemming rather than lemmatisation as the primary configuration. A lemmatiser looks words up in a dictionary and always returns a real word: producers gives producer, not produc. It is more accurate and much more pleasant to read. It is also more conservative — it will not merge produce and producer at all, because they genuinely are different dictionary words. The measurements decide it: stemming reaches macro F1 0.9197 and macro recall 0.9564; lemmatisation reaches F1 0.8650 and recall 0.8764. For a Boolean system where finding the family is the whole point, the aggressive option wins, and it wins because it is aggressive.

    What you now have

    Word families collapse to one term. jobs and job are now the same key. So are investment, investing and invest — all three become invest. The vocabulary shrinks sharply and recall rises.

    Chapter 4

    The dictionary

    Before you can look a word up, you need a list of the words that exist. That list, with a count or two attached, is the dictionary. It is small, and keeping it small on purpose is the point.

    The problem right now

    Chapter 3 gave us a way to turn any document into a list of terms. Run that over all 2,225 documents and you get 497,333 terms — but with enormous repetition. We need to answer questions that repetition hides:

    • Does the term oil exist in this collection at all? If not, the query oil AND price is empty and there is no point doing any work.
    • How many documents contain oil? Chapter 7 needs this number to decide which part of a query to evaluate first, and it needs it before touching any postings.
    • Which terms occur only once? Those are usually typos, foreign words or proper nouns, and knowing how many there are tells you how noisy the collection is.

    None of these questions need the actual document numbers. They only need the term list and some counts.

    The idea

    Split the two things apart. Keep a small dictionary holding every distinct term plus its counts, and keep the big postings — the actual document numbers — separately.

    Two different counts are needed, and confusing them is a classic mistake.

    • Document frequency, written df: how many documents contain the term, counting each document once no matter how often the word appears inside it.
    • Collection frequency, written cf: how many times the term occurs in total, across everything.

    The code

    What document 26 contributed, and what the dictionary says about it

    terms addedsteel, firm, cut, 45, 000, job, mittal, produc, execut, netherlands-bas, …
    df(steel)17 — only 17 of 2,225 articles mention steel at all
    df(job)231
    df(oil)110    cf(oil) = 304
    df(price)245    and document 26 is not among those 245

    Why it is built this way

    Decision: separate the dictionary from the postings. The class docstring gives the real reason from industrial practice: the dictionary is small enough to keep in memory, the postings are not. Here the whole thing fits in memory easily, so the split is not needed for size. It was kept anyway for two reasons. It makes it possible to answer "how big is the vocabulary?" without loading the index, which is what the report's before-and-after tables need. And it makes the ownership obvious: if you want to know whether a term exists, ask the dictionary; if you want to know where it is, ask the index.

    Decision: store both df and cf, even though df can be derived from the postings. The length of a postings list is exactly the df, so storing it is redundant. It is stored anyway because Chapter 7's optimiser needs to know how long a postings list is without fetching it — the whole point of the optimisation is to avoid touching large lists. If df required reading the list, the optimisation would cost exactly what it saves. The redundancy is also checked: Chapter 5's check_invariants raises if the stored df and the real list length ever disagree.

    What you now have

    A complete, sorted list of every term the collection contains, with two counts each, and a constant-time way to ask whether a term exists. Query planning is now possible, because the size of any term's answer is known before any work is done.

    Check yourself — nostop has 33,805 terms and mean df 10.542, while stemmed has 25,049 terms and mean df 13.383. Why did the average go up when the index got smaller?

    Because stemming merges postings lists rather than deleting them. When investing, invested and investment all become invest, three short lists become one longer one. The total number of postings does fall — 356,386 to 335,223 — because documents containing two members of the same family are now counted once instead of twice. But the number of terms falls much faster, from 33,805 to 25,049. Mean df is total postings divided by terms, so a small drop on top divided by a large drop on the bottom gives a bigger number. The average term is now genuinely more common, because the rare variants have been folded into their families.

    Chapter 5

    Turning the collection inside out

    This is the chapter the whole project is named after. One data structure, built once, that turns "search 2,225 files" into "read one list".

    The problem right now

    We have documents that know their words, and a dictionary that knows the words exist. What we do not have is a way to get from a word to the documents. Asking "which documents contain oil?" still means walking every document and checking — exactly the O(N) scan Chapter 0 rejected, just with better tokenisation.

    The data is stored the wrong way round for the question we want to ask.

    The idea

    What we have is a forward index: document → the words in it. What we want is an inverted index: word → the documents containing it. That is all "inverted" means — the mapping is turned inside out. The list of documents attached to one term is called its postings list, and each entry in it is a posting.

    The code

    Now the build. This is the only loop in the project that touches every token of every document, and it runs once.

    Finally, the safety net. Nothing calls this during normal querying — it exists so the test suite and the experiment script can assert that the two rules really do hold.

    Our running example after Chapter 5

    document 26no longer exists as a unit — its terms have been scattered into the rows of the index. It appears in the postings list of steel, of job, of mittal, and so on.
    oildf=110 → [2, 8, 11, 15, 21, 23, 24, 27, 29, 44, ... (+100 more)]
    pricedf=245 → [1, 3, 11, 14, 15, 21, 23, 27, 29, 41, ... (+235 more)]
    26 present?neither list contains 26 — the article never uses either word

    Why it is built this way

    Decision: sets during the build, sorted lists afterwards. The alternative is to append to a list and keep it sorted as you go, or to append freely and de-duplicate at the end. Keeping a list sorted during insertion means shifting elements on every insert, which is slow. Appending freely and de-duplicating later needs a separate pass and, more importantly, needs somebody to remember to do it. Using a set makes the duplicate rule structurally impossible to break rather than something the programmer must maintain.

    Decision: sorted by document number, not by anything else. A search engine that ranks results often stores postings ordered by importance instead. That was rejected because ranking is not part of this assignment — Boolean retrieval returns an unordered set — and because document order is what makes Chapter 6's linear merges possible. Ordering by importance would force every AND to fall back to a slow nested comparison. This single choice is the difference between the query engine being fast and being quadratic.

    Decision: no term positions and no term frequencies in the postings. A full system stores where in the document each word occurred, so it can answer phrase queries like "oil price". Storing positions would multiply the index size several times over and was left out because the assignment asks for AND, OR, NOT and parentheses, none of which need position. It is listed as a limitation in Chapter 10.

    What you now have

    The core of the system. Looking up oil now costs one dictionary lookup and reading a list of 110 numbers. It does not cost 2,225 file reads and 854,490 word comparisons. The cost of a lookup is now proportional to the size of the answer, not the size of the collection — which is exactly the property Chapter 0 said the naive scan lacked.

    110 vs 2,225 postings read to find every article mentioning oil, against files that would have to be opened by a brute-force scan. The whole stemmed index holds 335,223 postings across 25,049 terms and is built in a single pass over the corpus.
    Check yourself — suppose build used defaultdict(list) and .append() instead of a set. Name the two invariants that would break, and say which one Chapter 6 would notice first.

    Both would break. Duplicates would appear, because a word occurring three times in one document would append that document number three times. And ordering would still be fine, as it happens, because documents are processed in ascending order — which is what makes this bug so dangerous, since it would look almost correct.

    Chapter 6 would notice the duplicates first, and quietly. The intersection routine advances both pointers on a match, so a doubled entry on one side would leave a stray copy that then fails to match anything, and results would be missing rather than obviously wrong. That is precisely why check_invariants tests b <= a rather than b < a.

    Chapter 6

    Answering the query

    A user types oil AND price. That is a string. This chapter turns it into a tree, and turns the tree into a set of document numbers, without ever comparing two documents that do not need comparing.

    The problem right now

    We can look up oil and get 110 document numbers, and look up price and get 245. We cannot combine them. And oil AND price is the easy case — the query set also contains (microsoft OR apple) AND software and bank AND NOT football, which have structure that a flat left-to-right reading gets wrong.

    There is also an obvious but bad way to combine two lists. For each of oil's 110 documents, scan all 245 of price's looking for a match. That is 110 × 245 = 26,950 comparisons. The cost is the product of the two lengths, which is called quadratic, and it grows badly: doubling both lists quadruples the work.

    The idea

    Two ideas, one for structure and one for speed.

    Structure. Parse the query into a tree, called an abstract syntax tree. (microsoft OR apple) AND software becomes an And node with two children: an Or node and a Term. Once you have the tree, the grouping is settled and evaluation is a simple walk from the leaves upwards.

    Speed. Both lists are sorted. That is the gift from Chapter 5. Walk them together with one finger on each, like merging two piles of numbered cards:

    • If the two numbers are equal, it is a match — record it and move both fingers.
    • If the left number is smaller, that document cannot appear later in the right list, because the right list only goes up. Move the left finger.
    • Otherwise move the right finger.

    Every comparison advances at least one finger, and a finger never goes backwards. So the total number of comparisons can never exceed the sum of the two lengths — at most 110 + 245 = 355, not 26,950. That is called linear, and it is the entire reason postings are kept sorted.

    Why it is built this way

    Decision: recursive descent parsing, written by hand. The alternatives are a parser generator, or the shunting-yard algorithm converting to postfix notation. A generator would add a build step and a grammar file for a language with three operators. Shunting-yard is compact but the precedence lives in a table of numbers, which is much harder to read than three functions whose names are the precedence levels. With recursive descent, "NOT binds tighter than AND, which binds tighter than OR" is literally the order the functions call each other.

    Decision: keep the merges as explicit loops rather than using Python's built-in sets. set(a) & set(b) is one line and would be fast. It was rejected for two reasons. The assignment requires the Boolean operations to use the postings lists the system produced, and a set conversion throws the ordering away. And a set gives no way to count comparisons, which Chapter 7 must measure. Writing the loop is what makes the cost visible.

    Decision: difference instead of building a complement. Computing NOT football explicitly produces a list of 2,111 numbers, then intersecting that with bank's 186 costs thousands of comparisons. Measured on bank AND NOT football: the explicit route takes 4,299 comparisons, and difference takes 293. Same answer, 180 documents, both ways.

    What you now have

    A working search engine. Any query using AND, OR, NOT and brackets is parsed into a tree and answered from sorted postings lists, in time proportional to the lengths of the lists rather than their product.

    290 comparisons to answer oil AND price over the whole 2,225-document collection, returning 63 documents. The quadratic alternative would have needed 26,950 — about 93 times more work for exactly the same answer.
    Check yourself — intersect stops when either list is exhausted, but union keeps going with out.extend. Why the difference?

    Because of what each operator needs. For AND, a document must be in both lists, so once one list is finished no remaining document in the other can possibly qualify — there is nothing left to match against. For OR, a document only needs to be in either list, so everything left over still belongs in the answer. It is added without any comparison, which is why a union of two lists of length n and m costs at most min(n, m) comparisons rather than n + m.

    difference is the third case: it extends only a's tail, because documents left in b are exclusions with nothing left to exclude.

    Chapter 7

    Making it fast

    The query engine works. This chapter makes it do less work for exactly the same answer, using nothing but the document frequencies from Chapter 4 and the fact that AND is commutative.

    The problem right now

    oil AND price is fine, because it has only two arguments and there is nothing to reorder. Consider a three-term query instead, and evaluate it strictly left to right as written:

    querygovernment AND price AND oil
    step 1govern (490) ∩ price (245) → a middling intermediate result
    step 2that result ∩ oil (110) → 27 documents
    cost814 comparisons

    Now write the same query the other way round. Same answer, 27 documents, but:

    queryoil AND price AND government
    step 1oil (110) ∩ price (245) → 63 documents, already small
    step 263 ∩ govern (490) → 27 documents
    cost597 comparisons — 27% cheaper, purely because of the order the user happened to type

    The user should not have to know this. The system should choose.

    The idea

    An intersection can never be larger than its smallest input. If oil has 110 documents, then oil AND anything has at most 110 — there is no way to gain documents by adding another AND condition.

    So: process the smallest postings list first. The first merge is cheap because one side is short. The result of that merge is then bounded by the short list, so the next merge is cheap too, and so on. Every intermediate result stays small.

    Crucially, this can be decided before reading any postings, because Chapter 4 stored the document frequency in the dictionary. The plan costs a few dictionary lookups.

    The code

    First, a way to guess how big any subtree's answer will be, without evaluating it.

    Then the And branch of the evaluator, which is where the estimate is used.

    Read that first row honestly. Reordering a two-term AND saves nothing at all. The textbook claim "process the shortest list first" is about bounding intermediate results, and a two-term query has no intermediate results. Almost all of the measured saving in this project comes from the three negation queries, where deferring the NOT avoids building a 2,000-entry complement. That is a different mechanism wearing the same switch.

    Why it is built this way

    Decision: both strategies are kept, and both are always run. The experiment script executes every query twice, naively and optimised, and asserts that the two result sets are identical before recording any timing. An optimisation that changes the answer is not an optimisation, it is a bug — and a fast wrong answer is worse than a slow right one. The equality check is the correctness gate; the comparison counts only mean anything once it holds.

    Decision: measure comparisons, not just wall-clock time. Timing on a modern machine is noisy: garbage collection, caches and other processes move the numbers between runs. A comparison count is deterministic — run it a thousand times and get the same integer. The assignment asks for both, and both are reported, but the comparison count is the one you can argue from.

    Decision: estimate sizes rather than compute them exactly. The exact size of an OR subtree can only be known by evaluating it, which is the work we are trying to avoid. The sum-based estimate is sometimes too large, which means the optimiser occasionally picks an order that is not the true best. That is acceptable: the estimate costs a few dictionary lookups and the ordering it produces is right far more often than not.

    What you now have

    Query planning. The system now inspects a query before running it, chooses an evaluation order from the dictionary statistics alone, and gets provably the same answer either way.

    77,943 → 21,790 total comparisons across all 30 queries run against all five indexes — 150 query executions in total. That is a measured saving of 72.0%, with every result set verified identical between the two strategies.
    Check yourself — the sort key is (isinstance(c, Not), _estimated_size(...)). What would break if the two parts were swapped round?

    Negations would be ordered by their estimated size along with everything else, and a NOT of a rare term looks enormous — NOT chelsea is estimated at 2,225 − 69 = 2,156 documents. So it would sort last anyway, and by luck the common cases would still work.

    But it would break for a negation of a very common term. NOT said would be estimated small, sort first, and then the evaluator would have nothing to subtract from — it would fall into the Not branch of _evaluate and build the full complement, which is exactly the 4,000-comparison cost this optimisation exists to avoid. Putting the isinstance check first makes the guarantee unconditional instead of accidental.

    Chapter 8

    When the user cannot spell

    Everything so far assumes the user types a word that exists. This chapter handles the case where they do not — either because they typed a pattern with a star in it, or because they simply got it wrong.

    The problem right now

    Our running query, mistyped by one transposed letter:

    typedoil AND pirce
    looked uppostings("pirce") → []
    result0 documents. Not "did you mean"; not a warning. Silence.

    Chapter 5 made an unknown term return an empty list, which is logically correct and completely useless to a person. Measured over 20 deliberately misspelled queries, exact lookup reaches macro recall 0.1326 — it finds about one in eight of the documents it should.

    There is a second version of the same problem. A user who is unsure of a spelling, or who wants a whole family at once, might type gov*ment or comput*. Neither is a term, so both return nothing.

    The idea

    Both problems are "find the vocabulary terms that are nearly this string". Solve them the same way, in two stages:

    1. Generate candidates cheaply. Cut every vocabulary term into overlapping three-letter pieces and build a second index from piece to terms. A misspelling shares most of its pieces with the word it meant, so intersecting piece lists gives a shortlist of a few dozen terms.
    2. Verify candidates properly. The shortlist is only a shortlist — it contains wrong answers. Check each one exactly, with a regular expression for wildcards or with edit distance for misspellings.

    The pieces are called k-grams. With k = 3 the word price becomes pri, ric, ice. Padding it with a $ at each end adds $pr and ce$, which record that the word starts with pr and ends with ce. Without the sentinels there would be no way to express "begins with" — and comput* needs exactly that.

    The same recurrence as the code above, filled in cell by cell. The highlighted cells trace the cheapest route from the top left to the bottom right; the bottom-right cell is the answer.

    Our running example is one of the failures, and it is worth looking at properly. pirce shortlists piece and pierce at distance 1 and price at distance 2. Distance decides, so correct("pirce") returns piece, and oil AND pirce is repaired to oil AND piece, which retrieves 0 of the 25 relevant documents.

    Why distance 2 rather than 1? Because Levenshtein counts a transposition as two operations, not one — swapping ir for ri is a delete plus an insert. Damerau's variant of the algorithm adds transposition as a single edit, and would rank price first. That is the honest fix, and it is not implemented here. Two of the twenty misspelled queries fail this way; sahres is repaired to sales rather than shares for the same reason.

    The finding that mattered most: repair the surface form, not the stem.

    The obvious design is to correct query terms against the index you are going to search — the stemmed one. It fails badly, and quietly. goverment is a real misspelling in the test set. Porter's step 4 finds the suffix ment, checks that the surviving stem gover has measure 2, and strips it. So goverment stems to gover.

    And gover exists in the stemmed vocabulary, with document frequency 1. So nearest() hits its very first line, decides the term is spelled correctly, and returns it unchanged. The corrector never even looks at government. The misspelling is invisible to it.

    The fix is to run correction against the unstemmed surface vocabulary, then let the ordinary normaliser stem the repaired word before looking it up. goverment → government → govern, and the query works. Moving the correction step to surface forms is what took macro recall on the misspelled query set from 0.592 to 0.854.

    The 20 misspelled queries, summarised

    repaired17 of 20 correctly, including oill → oil, brodband → broadband, softwear → software, goverment → government, managment → management, microsft → microsoft
    failedpirce → piece, sahres → sales, labuor → labor
    notelabuor → labor is arguably right in American English and wrong for a British news corpus — the collection contains both spellings

    Why it is built this way

    Decision: one k-gram index serving two features. Wildcards could use a permuterm index, which stores every rotation of every term and answers a wildcard with a single prefix lookup. It is faster, but it only does wildcards, and it multiplies the vocabulary by the average word length. One k-gram index answers both requirements, and the code difference between them is just intersection versus union.

    Decision: generate then verify, rather than one exact algorithm. Running edit distance against all 33,805 terms for every query word is the alternative, and it is correct but wasteful. A term sharing no 3-grams with the query is almost never within two edits of it, so the k-gram shortlist throws away the overwhelming majority of the vocabulary for the cost of a few set lookups. The word "almost" is the trade: it is a heuristic, not a proof, and a pathological case could be missed.

    Decision: correct only unknown terms, and correct them silently. The experiment script only calls correct when a term is absent from the surface vocabulary. A system that second-guessed known words would break correct queries. The cost is that a real word typed by mistake — form when you meant firm — is never caught. That needs context, which a Boolean system does not have.

    Decision: the frequency discount is one edit, not a full ranking model. A proper noisy channel model would weight candidates by how likely each specific typo is, learned from data. There is no such data here, so a single blunt rule is used: a candidate the collection barely attests loses one notch. It is enough to stop the worst failures without pretending to a sophistication the evidence cannot support.

    What you now have

    A system that answers comput*, and that repairs most misspellings before they reach the index. Queries that previously returned nothing now return almost everything they should.

    Over 20 misspelled queriesMacro precisionMacro recallMacro F1
    Exact lookup, no repair0.19370.13260.1466
    With k-gram plus edit-distance repair0.80080.85430.8237
    0.1326 → 0.8543 macro recall on the misspelled query set. Precision rises as well, from 0.1937 to 0.8008 — because a query returning nothing scores zero precision, so repairing it improves both numbers at once.
    Check yourself — wildcard intersects k-gram sets but nearest unions them. Why must they differ?

    Because the two inputs mean different things. A wildcard's literal runs are promises: gov*ment guarantees the term starts with "gov" and ends with "ment", so every k-gram drawn from those runs must be present, and intersection is exactly right. It is also cheap, because each extra k-gram shrinks the candidate set.

    A misspelling makes no promises at all. pirce contains the k-grams pir and irc, and the intended word price contains neither. Requiring all of them would guarantee the right answer is excluded. Union asks only for some overlap, which is the most you can assume when the input is known to be damaged.

    Chapter 9

    How do we know it works?

    Every chapter so far has claimed an improvement. This chapter builds the ruler those claims were measured with, and is honest about what the ruler cannot measure.

    The problem right now

    oil AND price returns 63 documents on the stemmed index and 25 on the unstemmed one. Which is better?

    There is no way to answer that yet. "More results" is not better — returning all 2,225 documents would maximise results and be useless. "Fewer results" is not better either. You cannot compare two systems without first deciding, independently of both, which documents should have been returned.

    And the decision has to be made without looking at what either system produced, or you are simply marking your own homework.

    The idea

    Write down, for each query, the set of documents that genuinely answer it. That set is called the qrels, short for query relevance judgments. Then compare what the system returned against it.

    Two numbers, and they pull in opposite directions.

    • Precision asks: of what I returned, how much was right? It punishes rubbish in the results. Returning one correct document and nothing else gives perfect precision.
    • Recall asks: of what was right, how much did I return? It punishes things missed. Returning all 2,225 documents gives perfect recall.

    Either alone is trivially cheatable, which is why both are always quoted.

    Because two numbers are awkward to compare, they are combined into F1, their harmonic mean.

    The code

    Now the part that decides what counts as correct. It lives in queryset.py, and it is deliberately not allowed to know anything about the index.

    Our running query, scored

    queryq09 — oil AND price
    gold ruleall_of(w("oil"), w("price")) — the article must contain both words literally
    relevant25 documents
    stemmedretrieved 63, true positives 25 → P 0.3968, R 1.0000, F1 0.5682
    nostopretrieved 25, true positives 25 → P 1.0000, R 1.0000, F1 1.0000

    On this one query the unstemmed index wins outright, and the reason is instructive. The stemmed index conflates price, prices, priced and pricing into the single term price, so it returns 63 documents. The gold rule only accepts the literal word price, so the other 38 are counted as wrong.

    Are they actually wrong? An article about oil that says "prices rose" is plainly about oil prices. The gold rule says no because it was written to test literal matching. So this is not really the stemmer failing — it is the judgment being lexical. Over all 30 queries the stemmer still wins on macro F1, 0.9197 against 0.9044, because the morphological queries reward it more than the literal ones punish it.

    Why it is built this way

    Decision: relevance defined as a rule over raw text, not a hand-marked list. Hand-marking 2,225 documents against 30 queries means 66,750 human judgments, which is not feasible for a coursework assignment, and would be inconsistent besides. A rule is reproducible, auditable and re-runnable: anyone can read all_of(w("oil"), w("price")) and know exactly what was counted as correct.

    Decision: judge against raw text while retrieving from processed text. The module docstring calls this the point of the design. If the qrels were built from the stemmed index they would be defined by the very thing under test, and every system would score 1.0 against its own output. Keeping the two on different footings is what makes the comparison mean anything.

    Decision: report both macro and micro, always. Reporting only one invites cherry-picking. The gap between them is a finding in its own right — the stemmed index scores macro F1 0.9197 and micro F1 0.9166, which are close, meaning it performs consistently rather than being carried by a few large queries.

    The limitation, stated plainly, as the module docstring itself does. These judgments are lexical, not semantic. An article genuinely about the oil market that never writes the word oil — using crude, or Brent, or petroleum — is counted as non-relevant. That inflates precision, because a system is never punished for missing a document the rule did not know about, and deflates recall, because the relevant set is smaller than the truth.

    The saving grace is that it is wrong uniformly across all five indexes. Every system is measured against the same flawed ruler, so comparisons between them remain fair even though the absolute numbers should not be read as "this system finds 95.6% of what a person would want".

    A number for every claim in this walkthrough, computed the same way each time, from judgments that no part of the system could influence.

Stemming trades precision (1.0000 down to 0.9060) for recall (0.8686 up to 0.9564) and comes out ahead on F1. Lemmatisation is more precise than stemming but finds less.

    Check yourself — a system returns every one of the 2,225 documents for every query. What are its precision, recall and F1?

    Recall is a perfect 1.0, because every relevant document is certainly in there. Precision is terrible: for query q09 it would be 25 / 2225 = 0.0112. F1 is the harmonic mean, 2 × 0.0112 × 1.0 / (0.0112 + 1.0) = 0.0222 — almost zero.

    That is exactly why F1 is the headline number and why the mean is harmonic. The arithmetic mean would have given this useless system 0.51, which is more than half marks for doing nothing at all.

The stemmer's failures are in Chapter 3, the two-term optimisation's null result is in Chapter 7, the pirce misfire is in Chapter 8, and the lexical judgments are admitted in Chapter 9.     5 known limitations listed below rather than left for a marker to find.

    The five known limitations

    1. The stemmer splits families it should join. technology gives technologi while technological gives technolog, so one family occupies two dictionary entries with document frequencies 241 and 16. player never reaches play, because play's measure is 1 and step 4 demands more than 1. And one becomes on, colliding with a preposition. These are properties of the published 1980 algorithm, confirmed against NLTK in the test suite, not implementation bugs.
    2. Case folding destroys real distinctions. US the country and us the pronoun become one term, which is the second most frequent term in the whole collection at 3,478 occurrences. Same for Apple and apple. Recovering the distinction needs truecasing, which is a research problem rather than a switch.
    3. Edit distance does not know about transpositions. Levenshtein charges two edits for a swapped pair, so pirce is nearer to piece than to price and the repair goes wrong. The Damerau variant treats a transposition as one edit and would fix this. Two of the twenty misspelled queries fail for exactly this reason.
    4. No positions, so no phrase queries. The postings hold document numbers only, so "oil price" as an exact phrase cannot be answered, and neither can proximity searches. Adding positions would multiply the index size several times over and was outside the brief.
    5. The relevance judgments are lexical, not semantic. An article about the oil market that writes crude instead of oil is scored as non-relevant. This inflates precision and deflates recall for every system measured — but it does so uniformly, so comparisons between the five configurations remain valid even though the absolute figures should be read with care.
    Check yourself — you want to add phrase search, "oil price" meaning the two words adjacent. Which chapters change, and which do not?

    Chapter 5 changes most. A posting stops being a bare integer and becomes a document number plus the list of positions the term occupies in it. build must track the position of each token as it walks the document, so the inner loop needs enumerate.

    Chapter 6 gains a new merge alongside intersect: after finding a document in both lists, walk the two position lists together looking for positions exactly one apart. That is another two-pointer merge, one level down, and it works for exactly the same reason — positions, like document numbers, are stored in ascending order.

    Chapters 1, 2, 3, 4 and 9 do not change at all. Loading, tokenising, stemming, the dictionary and the scoring are all indifferent to what a posting contains. Chapter 7 would need a small addition, since the cost of a phrase merge depends on position-list lengths that df does not capture. That is a fair test of whether the layering was worth it: five of nine modules untouched by a significant new feature.
